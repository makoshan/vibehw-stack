# 自写网格寻路换 Rust 核心，和布线加速选型

**适用情形**：Freerouting 在「板上已有大量锁定铜、只补跨块连线」的板上不收敛（原力手环 C08B P42：现有铜锁住后冲突一直是 4231 处），只好自己写 Python 网格 A* 来补线；结果能布通，但一块板要跑几分钟到几十分钟，扫参数很慢。

## 1. 只换 A* 主循环，其余不动

- 先计时，再动手。P42 的 m3 板有 89 对端点：Python 版每对用时加总 235.1 s；同一个 A* 换成 Rust 后 19.2 s，寻路这一步墙钟 22 s。所以 Python 版九成以上的时间都花在 A* 主循环（heapq 加逐格扩展）上。距离变换、掩膜、光栅化本来就是 scipy、PIL 的 C 代码，不用换。
- 接口用 **ctypes + cdylib**，不用 PyO3 或 maturin：`cargo build --release` 一条命令出库，Python 侧不用装任何新包。数组一律 `np.ascontiguousarray` 按 uint8、float32、int64 传指针，返回扁平下标路径。核心代码在 `scripts/grid_astar/`，导出 `astar(h, w, tok, vok, start, goal, pen, layer_cost, via_cost, via_gap2, gbox, time_limit, max_expand, out, out_cap, out_len, expanded)`，返回 0 找到 / 1 超时 / 2 无路径 / 3 缓冲不够。
- 用环境变量切换（`ASTAR=rust`），Python 版留着做对照；调用方、拆线重布、DRC 都不改。
- 找库文件时只认 `.dylib` 或 `.so`：`target/release/` 里还有 cargo 生成的 `.d` 依赖文件，写成 `glob("lib*.*")` 会先匹配到它，dlopen 报「not valid mach-o」。

## 2. 等价门：逐对全等，再谈速度

验收顺序：同一块板、同样参数，**每一对的结果、每段线、每颗孔都相同** → 原生 DRC（`--refill-zones`）→ 间距反例 → 才看速度。只比「布通数差不多」不够：路径一变，后面的网就全变了。

**坑：照搬 Python 原型的实际数值类型，不是你以为的类型。**
- **情形**：Python 原型混用 numpy 标量和 Python float，NumPy ≥ 2 按 NEP 50 规则，Python float 是「弱类型」，跟着 numpy 标量走。
- **规则**：在原型里对真实表达式打 `type()`，确认每个量是什么类型，Rust 里逐个照抄。P42 的实际情况：
  - 罚分数组是 float32，所以代价 g 是 **float32**（`gc + c*LC*(1+pen)`，`c*LC` 先按 float64 算，再转 float32 参与运算）；
  - 起点坐标来自 `np.nonzero`，是 int64，所以启发值 h 是 numpy **float64**；`f = g + h` 是 float32 加 float64，升成 **float64**；
  - 优先队列按 `(f, g, l, y, x)` 元组的顺序比较，Rust 的 `Ord` 要照这个顺序写。
- **证据**：2026-10-26 P42 m3 上 89 对：
  - 全用 float64：分叉从第 6 对开始，布通 84/89（Python 是 86/89）；
  - 全用 float32：分叉推到第 11 对，85/89；
  - g 用 float32、f 用 float64：**0 对不同**，86/89。另一次运行导出的第二份 geom.json 上，同样 0 对不同。
- **置信**：中（一块板实测三轮，原因都能解释）。

**整条流程从头跑两遍，本来就不逐个相同，别拿它当等价门。** 待布的端点对来自 `kicad-cli pcb drc` 的未连接项，同一处未连接，KiCad 每次挑出来的端点可能不同（P42：+3.3V 一次给过孔，一次给 FPC2 焊盘）。从头跑两遍（导出 geom.json 在寻路之前，和用哪种 A* 无关），m3 完全相同，geom.json 里却有 10 对端点不同，路径从第 7 对起就分叉了。等价门只能用**同一份 geom.json** 做；整条流程只比质量：DRC、未连接数、旧连接丢失（低：一块板上观测一次）。

## 3. 换机器跑：超时按格数，不按秒

- **情形**：每对寻路设了墙钟超时（P42 是 60 s），再把同一流程搬到单线程更慢的机器上并行扫参。
- **规则**：跨机器比较、扫参时，超时一律按扩展格数封顶（`MAX_EXPAND`），不看墙钟；默认仍按墙钟，本机行为不变。搬到新机器先做一次快速检查：同一份 geom.json 跑一遍，和本机结果逐对比较，全等才派正式单。
- **证据**：10-26 Spark 第一轮扫参用的是 Python 版加 60 s 墙钟，大量对 `TIMEOUT`（抽查 b0、f4r4s、f16r8l 三组的寻路日志，末行都是 TIMEOUT），而同一几何在 Mac 上没有一对超时；52 分钟连第一轮寻路都没跑完，整单作废。换成 Rust 核心后，在 Spark 容器里 89 对和 Mac 零差异，每对加总 10.4 s。
- **置信**：低（一轮扫参作废，只见过一次）。
- **DRC 报告里的描述文字随界面语言变，脚本别靠它认对象。** Mac 上的 KiCad 输出中文（「走线」「过孔」「填充区」），Spark 容器的语言环境是 POSIX，输出英文。P42 的清撞铜脚本按「走线」「过孔」前缀挑要删的对象，在 Spark 上一个都没删（`removed 0`），15 组全部 32～39 处违规。改成按 DRC 项的 `uuid` 回板上取对象、按类型判断（`GetTracks()`、`Zones()`）；在一块有 50 个待删对象的真实中间板上，新旧写法挑出的结果完全一样。网名、层名用 `[网名]`、`F.Cu` 这类不随语言变的部分抽取（低：只见过一次；那次等价检查证明的是修法，不是这个现象出现了两次）。
- **Linux arm64 的库**：Spark 的 KiCad 容器里没有 cargo、gcc、curl。在 Mac 上用 `rustup target add aarch64-unknown-linux-gnu`，再拿 zig 当链接器：`zig cc -target aarch64-linux-gnu.2.28`，包装脚本要滤掉 rustc 默认带的 `--fix-cortex-a53-843419`，zig 不认这个参数。编出来的 `.so` 放到 `target/release/`，随推送目录一起带过去。

## 6. 顺序寻路卡住：改协商拥堵（PathFinder）

**情形**：自写网格 A* 一条一条布，先布的线堵死后布的路；「卡点 1.2 mm 内全拆」的拆线重布在卡点很多时等于推倒重来，扫参改不了排名。
**做法**：Rust 核心加 `astar_pf`（走线罚分按层 `[3][h][w]`，打孔附加代价 `[h][w]`；`astar` 签名与数值不变）。外层驱动见原力手环 `v12/c08a-v4-vendor-copper-20261026/grid/pf_route.py`：固定铜仍是硬障碍；新线之间不硬挡，每条线按间距规则往外胖一圈记成占用，别网进占用区按 `(1+历史)×(1+PF×占用网数)` 加价，PF 每轮乘上去；每轮只拆重布有冲突的网；收尾按冲突格数从多到少删，删掉的在硬避让下顺序补一遍，自检两两无冲突才写输出。

| 规则 | 证据（原力手环 C08A V4 m3，347 对，0.05 栅格） | 置信 |
|---|---|---|
| 先测「只看固定铜，每对单独能不能通」：几乎全通就说明卡点是互相挤，协商对症；大批不通先改摆位或固定铜 | 346/347 单独可通，只 1 对被固定铜堵死 | 中 |
| 占用圈两侧判法必须是同一个数：孔↔别网线取 max(孔环到线, 钻孔到铜)；不对称时收尾补布会留下单边冲突。收尾加「两两无冲突」断言，不过不写输出 | 孔环到线 0.41 与钻孔到铜 0.46 混用时，断言当场抓到 143 / 148 个冲突格；统一后 0 | 中 |
| 端点块（本网焊盘铜）里的线心格不计占用、不算冲突，否则别网正常贴着焊盘走就成了永远消不掉的假冲突 | 改前收尾仍有冲突；改后通过 | 低 |
| 同网不同对之间也要守孔到孔（同网别对的孔周围禁孔），同位孔要去重 | 改前回板 DRC：`holes_co_located` 17、`hole_to_hole` 14 | 中 |
| 禁布区（板级 + 封装自带）和封装上的非焊盘阻焊开窗要导进几何当硬障碍，补地孔也要避开；否则清理删掉违规线，未连又涨回去 | 漏导时回板 m5 未连 71、带 `items_not_allowed` 19 / 阻焊桥 48，清理后 104；导入后 86、0 违规 | 中 |
| 冲突对数约 30 轮后进平台，再加轮数、换 PF 增速 / 历史系数 / 孔代价 / F 层代价只差几项；平台后去看冲突集中在哪个件，那是摆位问题 | Spark 12 组 40–60 轮：未连 80–92（本机复核最好组 80 / 0 违规）；冲突集中在电平转换 U2 到主控和 ADS 的走廊 | 低 |

数字（同一块 m3、同一台 Mac 的 KiCad 判）：顺序寻路 257 对通 → 未连 122；协商 30 轮 281 对 → 104；补上禁布区与同网孔距后 272 对 → 86；Spark 最好组 → 80。每轮 10–40 s（单进程）。Spark 与 Mac 的 DRC 在清理脚本修好中英文描述后对同一块板给出相同未连数。
**等价门**：`astar_pf` 传 `pen3 = 三层同一张 pen`、`vpen = 50×pen` 时，与旧 `astar` 在 40 对上逐对全等（非零罚分）；故意把 `vpen` 置 0，17 对不同。
